# protocol/ —— 协议契约目录

一份**语言无关**的设备消息契约。前端（TS）、Mock 网关（Node）、真实设备侧（C/嵌入式）读的是同一批文件，
而不是「前端一份 interface、网关一份常量、口头再对一次」。

```
protocol/
  constants.json          ← 机器可读常量（数值的唯一来源，两端 import）
  messages.schema.json    ← JSON Schema（draft 2020-12）：双向信封的结构与边界
  limits.md               ← 单位与边界表（人读）+ 为什么这么定
  errors.md               ← 错误码 / 关闭码 + 前端拿到它该干什么
  versioning.md           ← 版本与兼容策略（只增不删、适配层、bootId）
  README.md               ← 本文（怎么用 / 怎么改）
```

## 1、谁读哪一份

| 读者                            | 读什么                                    | 怎么用                                                                  |
| ------------------------------- | ----------------------------------------- | ----------------------------------------------------------------------- |
| 前端（`src/protocol.ts`）       | `constants.json` + `messages.schema.json` | 常量直接 import；结构/边界用 **Zod** 做运行时校验（网络数据一律不可信） |
| Mock 网关（`server/index.mjs`） | `constants.json`                          | 常量直接 import；出协议前按白名单挑字段                                 |
| 设备侧 / 嵌入式                 | `messages.schema.json` + `limits.md`      | 按 Schema 实现收发；边界表解释**为什么**这些数字是这样                  |
| 演示 / 面试讲解                 | `errors.md` + `versioning.md`             | 「失败怎么表达」「协议怎么演进」两问的答案                              |

## 2、为什么是「契约先行」而不是「前端先行」

- **端口不在前端手里**：设备的字段定义来自嵌入式侧，前端只能是消费方之一；先把结构写进语言无关的 Schema，三方再各自生成/实现，才不会出现「前端改了字段名，设备要重新烧固件」。
- **边界必须显式**：`-999` 是哨兵还是合法值、通道号从 0 还是 1 开始、电平是 dB 还是百分比 —— 这些「差一点就全错」的约定，写在代码注释里没人读，写在 Schema 里能被机器执行。
- **契约测试让它不是文档**：数值改了但某一端没跟上，`pnpm test` 会红（见下文）。**文档会过期，测试不会。**

## 3、数据流（一眼看清哪端定义什么）

```
protocol/constants.json ──┬──▶ src/protocol.ts ──▶ Zod 校验 + TS 类型 ──▶ React 容器 / 插件
                          │
                          └──▶ server/index.mjs ──▶ 生成快照 / 电平 / 频谱 / ack
                                                              │
                          messages.schema.json ◀──契约测试比对──┘
```

## 4、怎么改协议（按顺序，不会漏）

1. 数值类改动 → 只改 `constants.json`（两端自动跟随）；
2. 结构类改动 → 改 `messages.schema.json`，同时更新 `src/protocol.ts` 的 Zod（**两端都要改，契约测试会逼你对齐**）；
3. 补文档：`limits.md` / `errors.md` / `versioning.md` 中相关的一篇；
4. `pnpm test` —— 契约用例校验 `JSON Schema ↔ Zod ↔ constants` 三方一致、边界样例的接受与拒绝一致；
5. 破坏性变更（删字段 / 改含义）→ 先走 `versioning.md` 的废弃流程，再升 `protocolVersion`。

## 5、契约测试做什么（`tests/contract.test.ts`）

| 用例                                                     | 挡住什么                                     |
| -------------------------------------------------------- | -------------------------------------------- |
| Ajv 按 JSON Schema 校验「网关真实会发出的帧」            | 网关偷偷发了契约之外的东西（或漏了必填字段） |
| 同一批帧再走 Zod 校验，结论必须一致                      | 两端的严格程度漂移（一方放过、一方拒绝）     |
| 越界样例（电平 −1000、33 路通道、257 点波形）必须被拒绝  | 边界被某端悄悄放宽（放进来一条就够画坏界面） |
| `messages.schema.json` 的数值 == `constants.json` 的数值 | 改一处漏一处                                 |
| Schema 的消息类型集合 == Zod 判别联合的类型集合          | 新增消息只加一端                             |

> 契约测试的完整版还包括「前端只依赖契约内字段」这一条：拿 Schema 生成的样例帧喂给解析层，任何一处依赖契约外字段都会暴露。
> 目前由上面第 2、3 条覆盖（Zod 会把契约外字段剥掉，若业务代码依赖它，测试会拿到 `undefined` 而失败）。
