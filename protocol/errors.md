# 错误与关闭码（协议 v1）

> 码值定义在 [`constants.json`](./constants.json) 的 `wire.errorCodes` / `wire.closeCodes`（**唯一来源**，代码从这里取），本文是语义、归属与「前端拿到它该干什么」。
> 新增一个码 = 改 `constants.json` + 补本文表格 + 在两端至少一处真正用到它（**登记但没人发的码是负债**，见文末「约定」）。

---

## 1、三种「失败」先分清

| 形态       | 载体                             | 含义                                                    | 典型处理                                   |
| ---------- | -------------------------------- | ------------------------------------------------------- | ------------------------------------------ |
| 指令被拒绝 | `ack` 且 `ok=false`（带 `code`） | 「你这条指令我收到了、也没执行」—— 是**某条指令**的结局 | 不重发、回滚乐观值、按 `code` 给提示       |
| 协议层错误 | `error` 消息（带 `code`）        | 「你发的这东西我根本没法处理」—— 不指向某条指令         | 记日志/报警；通常是客户端 bug 或版本不匹配 |
| 连接被关闭 | WebSocket `close(code, reason)`  | 「这条管道没了」—— 与指令无关                           | 看 `code` 决定**重不重连**（见第 3 节）    |

> 这三者最容易混的是**第一种和第三种**：「指令没回 ack」看起来像「出错了」，其实它的正确语义是**状态未知**（可能设备执行了、只是回执丢了）——
> 所以重发的判据是「超时」而不是「失败」，而且**用同一个 seq 重发**，让设备端的幂等去重来消化重复。

## 2、业务错误码

| 常量名（`constants.json`） | 码     | 语义                      | `retryable` | 谁发出                                                 |
| -------------------------- | ------ | ------------------------- | ----------- | ------------------------------------------------------ |
| `deviceChannelNotFound`    | `1002` | 设备或通道不存在 / 未上线 | `false`     | 网关（`setMuted` / `setLevel` / `setGain` 寻址失败时） |
| `unknownMessageType`       | `4000` | 不认识的消息类型          | `false`     | 网关（收到未定义 `type` 时回 `error` 消息）            |

**码段约定**（新增码时按段归位）：

| 段     | 用途                                      |
| ------ | ----------------------------------------- |
| `1xxx` | 请求 / 寻址 / 参数（例：1002 找不到目标） |
| `2xxx` | 设备状态（例：离线、忙、升级中、只读）    |
| `4xxx` | 协议 / 框架（例：4000 未知类型）          |

**关于 `retryable`（诚实说明）**：实现里 `ack.ok=false` 一律**不重发** —— 读回来的失败多半是参数或寻址问题，重发不会变好。
所以 `retryable` 目前是**信息性**字段：设备侧表达「这个失败是不是暂时的」（比如 2xxx 段的『设备忙』显然是），留给上层将来做自动重试或提示文案；
**如果哪天要接「可重试失败自动重试」，判据就在这里，不用改协议**。

## 3、关闭码

| 常量名              | 码     | 谁发出                       | 语义                                     | 重连？  | 出现场景                                               |
| ------------------- | ------ | ---------------------------- | ---------------------------------------- | ------- | ------------------------------------------------------ |
| `normal`            | `1000` | 任意一端                     | 正常关闭                                 | ✅      | 用户点「主动断开」；心跳判死后主动关（伪装成正常断开） |
| `goingAway`         | `1001` | 网关                         | 服务端要走了（重启 / 停机）              | ✅      | 故障注入台「优雅断开 (1001)」                          |
| `abnormal`          | `1006` | **浏览器**（不是谁「发」的） | 连接异常中断，没有关闭帧                 | ✅      | 故障注入台「半开连接」（网关 `terminate()`）；拔网线   |
| `policyViolation`   | `1008` | 网关                         | 策略不允许（Origin 校验失败 / 鉴权失败） | ❌      | 网关 `upgrade` 阶段拒绝非法 Origin                     |
| `messageTooBig`     | `1009` | 网关                         | 单条消息超过服务端上限                   | ⚠️ 见下 | 目前很难触发（见下方说明）                             |
| `deviceOffline`     | `4001` | 设备网关                     | 设备已离线，连上来也没用                 | ❌      | 真实设备侧；Mock 网关未实现                            |
| `firmwareUpgrading` | `4002` | 设备网关                     | 固件升级中，稍后再来                     | ❌      | 真实设备侧；Mock 网关未实现                            |

**「重连？」这一列不是注释，是代码读的**：`client.reconnect.noRetryCloseCodes` 里列了 `1008 / 4001 / 4002` ——
它决定 reconnect 插件是「退避重连」还是「停下来，把原因显示给用户」。**重连也没用的场景硬要重连，只会变成刷日志的攻击。**

两处诚实的边界：

- `1009`（超大消息）**当前不在不重连名单里**。网关也没设 `maxPayload`（`ws` 默认 100 MiB），所以现实里碰不到 ——
  路线图里「超大消息 `close(1009)`」那条演示，就是先把上限调到能触发的量级，**顺便暴露「重连后发出同样的超长消息 → 又一次 1009」这个循环**，到那时该把它加进不重连名单。
- `4001 / 4002` 是**策略先落地、Mock 网关还没实现**的码：它们在 `constants.json` 里登记、被重连策略消费，但演示环境里没人发。
  真实设备（或它的网关）才是发送方。

## 4、与故障注入台的对照

| 注入            | 协议上的表现                                  | 前端应当观察到的                                          |
| --------------- | --------------------------------------------- | --------------------------------------------------------- |
| 优雅断开 (1001) | `close(1001, 'server going away')`            | 重连倒计时 1s→2s→4s…（带抖动，封顶 30s）                  |
| 半开连接        | 没有关闭帧；`readyState` 短暂停在 OPEN        | 心跳连续超时 → 判死 → 主动 `close(1000)` → 走重连         |
| 脏数据          | 非 JSON 帧                                    | `core:parse-error` 计数 +1，连接不受影响                  |
| 结构非法        | 合法 JSON、缺字段                             | `protocol:invalid`（Zod 报出前 3 条 issue），业务链看不到 |
| 指令不回 ack    | 网关吞掉指令（心跳除外）                      | 3s 超时 → 同 seq 重发 ×3 → `command:failed` → 乐观值回滚  |
| 未知类型        | 网关回 `error`（`unknownMessageType` / 4000） | 一条协议层 error，连接继续                                |

---

**约定**：新增错误码/关闭码必须同时做三件事 —— ① 加进 `constants.json`；② 补上本文表格（含「前端该干什么」）；③ 在代码里真正使用它。
只做前两件的是**文档债**，将来会成为「协议里有个码，没人知道什么时候发」的坑。
