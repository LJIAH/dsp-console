# 版本与兼容（协议 v1）

> 协议的「活着」的部分：固件会升级、浏览器会刷新，而**老前端要能控新固件、新前端要能控老固件**。
> 本文写清 v1 的兼容规则与演进流程；`version` 字段的值来自 [`constants.json`](./constants.json) 的 `protocolVersion`。

---

## 1、两个方向别混

| 方向                            | 含义                         | 场景                                         |
| ------------------------------- | ---------------------------- | -------------------------------------------- |
| 向后兼容（backward compatible） | 新版本能处理**旧版本**的数据 | 前端上线了 v2，用户家里的设备还是 v1 固件    |
| 向前兼容（forward compatible）  | 旧版本能**容忍**新版本的数据 | 设备升级到 v2 固件，用户浏览器里还是 v1 页面 |

日常说的「兼容」多半是前者，但这个 Demo 里后者同样真实：**设备端升级比前端慢**（前端刷新即新版，固件要现场升）。

## 2、v1 的兼容铁律

### ① 只增不改、不删字段

```
新增字段 → 旧端不认识它，忽略；新端认识，用它      ✅ 安全
删除字段 → 旧端还在发，新端已经不期待了            ❌ 危险
改字段含义 → 同名不同义，数值错得毫无提示          ❌ 最危险
```

宁可新增 `levelPercent`，也不要把 `level` 的含义从 dB 改成百分比。**「同名不同义」是最隐蔽的一类事故**：代码不报错，数字全错。

### ② `version` 每帧带，缺省视为 1

- 两端都发 `version`（当前 = `1`）；接收端按 `msg.version ?? 1` 处理 —— **缺省即 v1，所以 v1 的帧不带它也能过**；
- 为什么不是「连接时协商一次」：滚动升级期间同一网段会同时存在两代固件，**同一条连接内**也可能先后到达两代帧；每帧带版本才能逐帧判断。代价一帧十几字节，相对批量帧可忽略。

### ③ 老字段「保留 + 标记废弃」，不立刻删

过渡期内旧字段照常发（标 `deprecated` 语义），等旧固件退役后再删。删的那一刻才是真正的破坏性变更。

## 3、前端的两条纪律：解析边界宽容，使用前兜底

| 位置         | 纪律                                                                   | 落点                                                                |
| ------------ | ---------------------------------------------------------------------- | ------------------------------------------------------------------- |
| **解析边界** | 宽容：未知字段忽略/剥掉，新增字段一律 `optional`，**不做 `.strict()`** | `src/protocol.ts` 的 Zod schema（默认 strip，多余的键被剥掉不报错） |
| **使用前**   | 兜底：`??` 默认值，保证业务代码永远拿不到 `undefined`                  | `levelCodec.fromWire()`（哨兵 → `null`）、UI 侧 `ch?.gain ?? 0` 等  |

「宽容」是为了**别把合法的旧消息拒之门外**，「兜底」是为了**别让业务代码拿到 undefined** —— 一个管进门的门槛，一个管进门后的保险，位置不同，不矛盾。

反过来说，**严格只出现在发送方**：网关出协议前显式挑字段（白名单），内部模拟字段（`base`）绝不外泄。别人发来的东西宽容，自己发出去的东西严格。

## 4、版本差异收敛到一处（适配层）

所有入站帧都过同一个入口：

```
WebSocket 帧 → 内核 JSON.parse → 协议插件 ServerMessageSchema.safeParse → 业务链
                                     ↑
                        适配层就落在这里（src/protocol.ts）
```

目前只有 v1，所以没有 `if (version === 1) … else …` 的分支 —— 但**结构已经就位**：将来 v2 到来时，分派写在 `parseServerMessage` 里，业务代码（组件、插件）一行都不用改。

> 反模式：在每个组件里判断版本。加一个版本要改几十处，必漏。**迁移逻辑必须收敛到一个函数。**

## 5、`version` 撑不住的那类变化：设备重启 / 掉电 / 出厂恢复

字段没变、版本没变，值却全变了 —— `version` 检测不出来。这类只能靠**另外两个判据**：

| 事件        | 协议表现                               | 前端必须做的事                                                       |
| ----------- | -------------------------------------- | -------------------------------------------------------------------- |
| 掉电 / 重启 | 连接断开；**未落盘的配置丢失**         | 重连后**不沿用本地缓存**，重新拉一次全量（session 插件的快照对齐）   |
| 出厂恢复    | 配置全量重置，连接**可能不断**         | 靠 `bootId` 变化判断：变了就清缓存 + 拉全量                          |
| 固件升级    | 设备可能多次重启、能力集（通道数）变化 | 升级完成后按新的 `device.channels.length` 重排界面，而不是沿用旧列数 |

`bootId` 是**本次上电的 ID**（不是设备 ID）：设备重启后它会变，所以「`bootId` 变化」= 「你手里那份状态已经不作数了」。界面上它显示在设备列表里，是这一判断的可视入口。

## 6、改动协议时的流程（照这个顺序，不会漏）

1. **改 `protocol/constants.json`**（数值）或 **`messages.schema.json`**（结构）；
2. 两端跟随：`src/protocol.ts`（Zod + 类型）、`server/index.mjs`（生成与夹取）—— 都从 `constants.json` 取值，所以数值只改一处；
3. 补文档：`limits.md` / `errors.md` / 本文；
4. `pnpm test` 跑契约用例（`JSON Schema ↔ Zod ↔ constants` 三方一致 + 边界样例），红了就说明有地方没跟上；
5. 变更**通知设备侧**（人读契约就是 `messages.schema.json`），破坏性变更同时升 `protocolVersion`。

**未实现、但已经想清楚的下一步**（不要当成现状）：

- **能力协商帧**：连上后由设备发一次能力集（支持哪些消息、通道数上限、固件版本），前端据此选装插件 —— 目前通道数是从 `snapshot` 的 `channels` 长度倒推的，够用；
- **固件升级抑制重连风暴**：设备在升级期间回 `4002`（已在 `closeCodes` 里登记、也被不重连策略消费），真实网关还没实现发送端。
