# 单位与边界（协议 v1）

> **数值的唯一来源是 [`constants.json`](./constants.json)**（机器读，两端 import）。本文是它的人读版本 + 为什么这么定。
> 改数值只改 JSON，但**必须同步本文与 [`messages.schema.json`](./messages.schema.json)** —— `pnpm test` 里的契约用例会校验 `constants.json ↔ JSON Schema ↔ Zod` 三者一致，漏改会红。

---

## 1、信封

| 字段      | 类型              | 必填 | 说明                                                                |
| --------- | ----------------- | ---- | ------------------------------------------------------------------- |
| `type`    | string            | ✅   | 消息类型，决定 payload 的形状（判别联合的判别式）                   |
| `ts`      | number            | ✅   | 发送方本地毫秒时间戳。**只用于展示与排序，不做时钟对齐**            |
| `seq`     | integer ≥ 1       | ❌   | 只出现在两类消息上：`meters`（全局单调，跳号 = 缺口）与「可靠指令」 |
| `version` | integer，缺省 = 1 | ❌   | 协议版本。见 [`versioning.md`](./versioning.md)                     |

**为什么 `version` 每帧都带**，而不是「连接时协商一次」：滚动升级期间同一网段会同时存在多代固件（且浏览器端是「刷新即新版」，设备端是「升级才新版」），
每帧带版本才能对**同一连接内先后到达的两代帧**分别判断。代价是一帧十几字节，相对 20Hz × 多通道的批量帧可以忽略。

## 2、单位与边界

| 字段                   | 单位      | 范围                            | 哨兵 / 步进           | 谁在约束它                                 |
| ---------------------- | --------- | ------------------------------- | --------------------- | ------------------------------------------ |
| `channel.level`        | dBFS × 10 | `-600 ~ 0`（即 −60.0 ~ 0.0 dB） | 哨兵 `-999` = 无信号  | 网关夹取；前端 Zod 校验；`levelCodec` 换算 |
| `channel.gain`         | dB        | `-12 ~ +12`                     | 步进 `0.5`（UI 手感） | 网关 `clampGain` 归一到 0.5                |
| `channel.ch`           | 序号      | `1 ~ 32`（**从 1 开始**）       | —                     | 前端 Zod；网关按下标寻址                   |
| `channel.muted`        | boolean   | —                               | —                     | —                                          |
| `channels`（数组长度） | 路数      | `1 ~ 32`                        | —                     | **= 设备能力**，见下                       |
| `spectrum.bins`        | 字节      | `0 ~ 255`，**固定 64 个**       | —                     | 前端 Zod `.length(64)`；网关定长生成       |
| `waveform.samples`     | 字节      | `0 ~ 255`，**固定 256 点**      | 中轴 `128`            | 前端 Zod `.length(256)`；网关定长生成      |

### 2.1 为什么电平是「×10 定点整数」

- **省字节**：`-405` 比 `-40.5` 少 3 个字符；20Hz × 16 通道 × 10 台设备，这个差异是每天的量级。
- **比较不需要浮点**：C 端（嵌入式网关）少一次 `float` 解析与格式化，前端也少一次浮点误差判断。
- **跨语言一致**：`-40.5` 在 JSON 里是「十进制字面量」，落到 IEEE754 再乘回来，边上不保证相等；定点整数没有这个问题。

### 2.2 为什么用 `-999` 哨兵，而不是 `null` / 省略字段 / `0`

| 方案          | 问题                                                                         |
| ------------- | ---------------------------------------------------------------------------- |
| 省略字段      | 「字段缺失」与「值为空」两件事挤进一个表达，接收端到处 `in` 判断             |
| `null`        | 数组里放 `null` 会被打回动态类型；批量帧里也不想为它特殊处理                 |
| `0`           | **0 dBFS 是满刻度**，不是静音 —— 拿 0 表示无信号，等于把「峰值」当「没信号」 |
| **`-999`** ✅ | 落在合法域（−600 ~ 0）之外、物理上不可能出现，因此**不歧义、不占额外字段**   |

前端拿到的不是 `-999`，而是 `null`：`levelCodec.fromWire()` 在一处把哨兵翻译成「无信号」，业务代码不必认识这个魔术数字。

### 2.3 dBFS 的两条语义（解释「为什么表盘很少到 0」）

- `0 dBFS` = 满幅**方波**（数字域的最大值）；
- 满幅**正弦**的 RMS 是 `1/√2 ≈ 0.707` → `20·log₁₀` ≈ **−3 dBFS**。

设备 DSP 与浏览器本地分析（`AnalyserNode` → RMS → `20·log₁₀`）走的是同一套算法，所以两个数据源的电平可以放在同一张表上比。

### 2.4 为什么通道数是「设备能力」而不是界面常量

`ADSP1616` 是 16 进 16 出、`ADSP0808AEC` 是 8 进 8 出。界面的列数、推子的个数、批量帧里 `levels` 的长度**全部跟着 `device.channels.length` 走** ——
一旦把 16 写成前端常量，接第二种机型时就是「多出来的 8 列全是空槽」或者「8 路的设备只能控制前 8 路」。`32` 是防畸形数据的护栏，不是业务上限。

### 2.5 `level` 与 `gain` 是两个字段（控制量 vs 测量值）

- `level` 是**测量值**：设备实测的电平，**不可设定**（它由输入信号和增益共同决定）；
- `gain` 是**控制量**：可以设的值，推子控制的必须是它。

演示里能直接看出这个区别：拖推子 → 网关把 `gain` 真的算进电平生成（`level = base + gain×10 + noise`）→ 电平柱跟着抬起来。
如果拿 `level` 当控制量，就会出现「设了 6dB，下一帧设备报回实测 −23dB」的鬼故事。

## 3、节拍（谁多久推一次）

| 内容                      | 周期           | 由谁推          | 备注                                                  |
| ------------------------- | -------------- | --------------- | ----------------------------------------------------- |
| 电平 `meters`             | 50ms（20Hz）   | 网关 → 全部     | 全设备总览；小帧，必推                                |
| 频谱 / 波形               | 100ms（10Hz）  | 网关 → 被聚焦的 | 大帧（64+256 个数），**按需**：`focus` 指令决定推给谁 |
| ws 协议层 ping 巡检       | 30s            | 网关 → 浏览器   | 对前端透明（浏览器自动回 pong），用于清理死连接       |
| 应用层心跳 `ping`         | 15s            | 浏览器 → 网关   | 半开连接的唯一探测手段（浏览器发不出协议层 ping 帧）  |
| 拖动预览 `setGainPreview` | ≥60ms（≤16/s） | 浏览器 → 网关   | 节流后发送；可丢、不入队、不回 ack                    |

## 4、超时、重试与队列

| 参数                | 值                               | 语义                                                                 |
| ------------------- | -------------------------------- | -------------------------------------------------------------------- |
| ack 超时            | 3s                               | 超时后**用同一个 seq** 重发 —— 所以设备端必须按 seq 幂等去重         |
| 重发次数            | 3                                | 3 次仍无 ack → `command:failed`，Promise reject（UI 据此回滚乐观值） |
| 心跳超时 / 判死阈值 | 5s / 2 次                        | 连续 2 次未收到 pong 才判死 —— 一次超时可能只是抖动                  |
| 判死动作            | `close(1000)`                    | 主动关（不是 1006）：把半开连接伪装成正常断开，好让重连流程接管      |
| 重连退避            | 1s 起，×2，封顶 30s，带 50% 抖动 | `delay ∈ [exp/2, exp]`，避免多客户端同时回来打垮网关                 |
| 不重连的关闭码      | 1008 / 4001 / 4002               | 策略违规 / 设备离线 / 固件升级中 —— 重连也没用（见 errors.md）       |
| outbox 队列上限     | 200 条                           | 断线补发队列；超出丢最旧。`setGainPreview` 这类易失消息**不入队**    |
| 背压高水位          | 5 MiB                            | `bufferedAmount` 超水位就丢新消息（实时数据丢一条可容忍）            |
| 乐观值等待上限      | 2s                               | 松手后等权威 `state`；等不到就交还（state 丢了不能把推子冻住）       |

## 5、校验分层：谁在哪一层拦什么

| 层                  | 位置                         | 拦什么                           | 失败后果                                  |
| ------------------- | ---------------------------- | -------------------------------- | ----------------------------------------- |
| ① 内核 `JSON.parse` | `core/ws-core.ts`            | 非 JSON 的脏帧                   | 丢弃 + `core:parse-error`（连接不受影响） |
| ② 协议插件（Zod）   | `plugins/protocol.ts`        | 能解析但**结构/边界非法**的消息  | 消费掉 + `protocol:invalid`，业务链看不到 |
| ③ 渲染 / UI 层      | `MeterCanvas` / `GainFaders` | 值域夹取（画出界值也好过丢整帧） | 夹到合法范围                              |

两个刻意的「不严格」：

1. **`meters.levels` 只校验形状（整数数组、长度合规），不校验值域** —— 高频通道上宁可把一个越界值画成满格，也不能因为一条越界值的行李把整帧丢掉；值域由渲染端夹取。
2. **收到未知字段一律容忍**（Zod 剥掉多余的键、JSON Schema 不禁止额外字段）。这是「固件先上线、前端后跟上」的现实路径，也是向前兼容的落点（见 `versioning.md`）。

而「严格」只出现在**发送方**：网关出协议前显式挑字段（`cloneChannel` 白名单），内部字段（如模拟用的 `base`）绝不外泄。

## 6、这份边界表怎么被「强制」

不是靠自觉，是靠测试（对应 `协议设计/06` 的契约测试）：

```
protocol/constants.json  ──┬─▶  src/protocol.ts（Zod 边界）
                           ├─▶  server/index.mjs（生成与夹取）
                           ├─▶  protocol/messages.schema.json（JSON Schema 边界）
                           └─▶  protocol/limits.md（本文）
                                       │
                                       ▼
                      tests/contract.test.ts：四者不一致就红
```

契约用例做三件事：**① 用 Ajv 按 JSON Schema 校验网关真实会发出的帧；② 用 Zod 校验同一批帧，两者结论必须一致；③ 越界样例（−1000 的电平、33 路通道、257 点波形）必须被拒绝。**
